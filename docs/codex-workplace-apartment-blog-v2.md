운영 원칙: 기존 아파트 단지 글·TOP3·분양·Paramma·AI Price Atlas 기능 유지. 사용자 승인 전 프로덕션 배포 금지.

## 1. 무엇을 만드는가

아파트 이름으로 시작하지 않고 **직장·시설 이름으로 시작하는 이사 정보 블로그**를 만든다.

독자 흐름은 다음과 같다.
'내 직장 이름 검색' → '주변 실제 후보 단지 3~5곳' → '출퇴근 가능 여부' → '매매·전세·월세 실거래와 현재 호가의 차이' → '실거주 체크' → '어느 단지를 직접 확인할지 결정'

대상 직장 유형: 상업시설(스타필드·백화점·쇼핑몰), 산업단지·공장, 업무지구·기업, 병원·대학교 등.
특징: 주소나 광고성 시세 나열을 피하고 **근무지 출입구와 아파트 출입구, 검증된 주거비를 한눈에 비교**하는 독자 중심 콘텐츠.
검색량을 조사하지 않았으면 검색량이 높은 키워드라고 주장하지 않는다.

## 2. 초기 글 유형과 입력값

초기 MVP는 '근무지 주변 아파트 3~5곳 비교' 하나에 집중한다.
이후 단일 단지 심층 분석, 전세·월세 중심형, 교대·야간 근무형으로 확장 가능하도록 설계하되 초기 단계에서 메뉴를 과도하게 늘리지 않는다.

사용자 입력:
- 근무지 유형, 이름, 지역, 공식 주소, 실제 기준 출입구(모르면 needs_check)
- 이동수단(도보/대중교통/자동차), 희망 거리 또는 시간
- 거래유형(매매/전세/월세/전체), 예산(없으면 임의로 가정 금지)
- 후보 3~5곳(빈칸이면 조사 요청서에 후보 찾기, 자동 후보는 단지 식별 검증 후)
- 조사 기준일, 출처와 확인 메모
- 각 정보의 검증 상태(확인됨/확인 필요/자료 없음 또는 접근 불가 구분)

## 3. 완성 블로그 글의 고정 구성 — 가장 중요

[제목]
- 검색 유입을 위한 직장명 + 지역 + 아파트 + 독자 질문.
- 제목 3개 제안, 실제 검증 자료와 일치하는 제목을 1개 선택.
- 예: '스타필드 수원 근처 아파트 5곳, 출퇴근과 집값 비교'
- 미검증인데 '도보 10분', '20분 이내 TOP5', '1위 추천' 등 단정하지 말 것.

[도입: 짧은 3~5행]
'스타필드 수원에서 일한다면
어느 아파트부터 살펴볼까요?

가까워 보여도 출입구 위치와
집값은 단지마다 다를 수 있어요.

실제 자료를 기준으로
하나씩 비교해 보겠습니다.'
문체의 예시일 뿐 위치·가격의 검증을 대신하지 않음.

[01. 10초 핵심 요약]
- 근무지 정확한 주소와 출입구 확인 상태.
- 아파트 후보 3~5곳의 단지명, 정확한 주소, 준공연도, 대표 비교 전용면적.
- 한눈에 보는 표: 단지 / 면적 / 매매 실거래(계약일·층·해제 상태) / 전월세(있는 경우) / 현재 매물 호가(조회일) / 실제 경로 / 자료 기준일 / 출처 / 검증상태.
- 모르는 정보를 0원·0분·거래 없음으로 쓰지 않는다. 대신 needs_check로 표시한다.

[02. 어디에서 출퇴근하는가?]
- 근무시설 공식 주소와 보행·직원 출입구의 차이를 설명.
- 실제 출입구가 특정되지 않으면 확인 필요 명시.
- 자동차의 혼잡, 대중교통의 배차·환승, 도보의 실제 건널목과 출입문을 별도로 검증.

[03. 후보 아파트 3~5곳]
- 서로 비슷한 아파트 이름과 오피스텔을 구분.
- 주소(법정동·지번·도로명), 단지 식별, 준공/사용승인, 전용면적 확인.
- 단지별 '이 단지를 살펴볼 이유'를 한 문장으로, 자료로 확인되지 않은 장점은 만들지 않음.

[04. 실제 출퇴근 동선]
- 근무지 실제 출입구 ↔ 아파트 실제 출입구 사이의 경로 서비스 도보 경로가 확인된 경우만 거리·시간 표기.
- 기존 지도 서비스가 제공하는 지오코딩/직선거리를 도보 시간으로 바꾸지 않는다.
- 출입구, 야간 개방, 횡단보도 신호, 경사/주차 동선 등 미확인 조건은 현장 확인 항목으로.

[05. 실거래와 주거비]
- 국토부 매매 실거래: 정확히 같은 단지/전용면적의 계약일·층·금액·해제 여부 확인.
- 국토부 전월세 계약: 별도 공식 자료를 확보한 경우만 보증금·월세·계약일 표시.
- 현재 매물 호가: 매매/전세/월세 구분, 자료 조회일·출처·중복 가능성 표시.
- 계약 신고 가격 ≠ 현재 호가. 거래 유형과 면적을 섞지 않는다.
- 기간 중 거래가 없다면 수집 실패·조회 미완료인지 먼저 구분.

[06. 실거주 장단점]
- 야간 조명, 출입구 운영, 주말 쇼핑객 혼잡, 횡단보도, 소음, 주차, 건물 내부 이동거리 등 확인한 사실만 적음.
- 현장 검증이 없으면 '입주 전 확인할 점'으로 제시.
- 부동산 투자수익·가격 상승·하락 원인을 추정하지 않음.

[07. 독자에게 줄 특별한 발견 1개]
- 예: 동일 면적대라도 서로 다른 단지의 '개별 계약 사례'가 얼마 차이 나는지.
- 비교 기준일, 층, 면적, 유효 계약 여부와 조건 차이를 반드시 밝혀 일반 시세로 과장 금지.
- 비교할 데이터가 없으면 억지 발견을 만들지 말고 '확인해야 할 비교 포인트' 제시.

[08. Q&A 3개]
- 질문 1: 실제 출퇴근이 편리할까?
- 질문 2: 실거래가와 현재 매물 가격은 왜 다를까?
- 질문 3: 계약 전 꼭 확인할 사항은?
- 답변은 실제 확인 자료에 따라 작성. 미확인 항목은 명확히 구분.

[09. 결론·3줄 요약·출처]
- '누구에게 어떤 조건을 확인할 만한가'를 안내. '무조건 추천 1위' 금지.
- 3줄: 출퇴근 검증 범위 / 주거비 핵심 차이 / 남은 현장 확인.
- 데이터마다 기준일과 출처 링크. 마지막에 자료 출처 요약.
- 해시태그 7~10개.
- 'YYYY.MM.DD 기준 · 국토부 실거래 자료' 문구는 국토부 자료를 실제 확인한 경우에만 쓴다.

## 4. 글쓰기 문체와 모바일 레이아웃

- 친근하지만 신뢰감 있게, 실제 블로그 운영자가 정리한 말투.
- 1~2행 단위 짧은 문장, 한글 약 15~20자 수준의 의미 단위 줄바꿈, 문단 사이 빈 줄 충분히.
- 설명글을 길게 늘어놓지 말고 '이미지 한 장 → 설명 2~3줄 → 다음 이미지' 흐름.
- 중요한 강조는 1~3개 정도로 절제.
- 네이버에서 사용자가 직접 가운데 정렬하므로 자동 가운데 정렬 기능은 만들 필요 없음.
- 이미지 없이 장문의 문단이 이어지는 구조 피하기.

## 6. 개발 구현 우선순위

[1단계/P0 — 우선 작업] 기존 app/apartment-workplace/page.tsx 개선
- 이미 있는 연구 요청서(buildResearch), 원고 요청서(buildArticle), localStorage 저장 기능 유지.
- 위 본문 고정 구성, 10초 비교표, Q&A 3개, 이미지 00~07 요청서 문자열 생성기 반영.
- 자료 부족 때 완성글처럼 꾸미지 않고 확인 필요 안내.
- 조사 요청서 한 번 복사 / 최종 원고 한 번 복사 / 이미지 슬롯별 복사 / ChatGPT 열기.
- 출처 원문과 체크박스를 분리. 체크 표시만으로 verified 상태가 자동 부여되면 안 됨.
- 기존 복잡한 UI를 정리하되 다른 메뉴·기능을 무단 삭제하지 말 것.

[2단계/P1 — 국토부 매매 데이터 연결]
- 기존 lib/apartment-server.ts, apt_complexes, apt_trades를 재사용.
- 기존 국토부 RTMSDataSvcAptTrade는 아파트 **매매** 신고 자료임을 유지.
- 동일 단지 식별, 전용면적 정확 일치, 계약일, 층, 금액, 해제 표시, 수집일 확인.
- apt_monthly_stats의 area_group(면적대 그룹)을 개별 거래 면적과 동일시하지 않는다.
- 취소 계약은 유효 최고가 비교에서 제외.
- 서버에서 안전하게 조회하고 API 키/관리자 DB 키를 브라우저에 노출하지 않는다.
- Codex용 read-only API 조회 기능은 기존 PR #97 내용을 확인하여 중복 구현/충돌 방지.
- P0와 별도의 변경 묶음·PR 권장.

[3단계/P2 — 후속 연결]
- 전월세 공식 API, 현재 공개 호가, 도보 경로 API는 각각 별개의 소스로 구성.
- 실제 경로 서비스나 현황 매물 취득 권한·약관이 확인되기 전 자동 수집 가정 금지.
- app/api/apartment/map, app/api/apartment/nearby 의 현재 좌표/직선거리를 도보 경로로 잘못 사용 금지.
- 미연결이면 화면·원고에서 needs_check를 유지.

## 7. 구조화된 근거 모델

각 주장/숫자별로 value, unit, sourceName, sourceUrl, checkedAt, status(verified / needs_check / unavailable), note를 저장하거나 가공한다.
추가 필드:
- workplace: 이름, 공식주소, 실제 출입구/출입구 확인상태.
- complex: 정확한 단지 ID/이름/주소/사용승인일/전용면적.
- trade: 거래유형, 전용면적, 계약일, 층, 가격, 해제 여부, 출처, 수집시각.
- listing: 호가, 거래유형, 보증금, 월세, 매물 확인일, 중복 여부.
- route: 이동수단, 출발/도착 출입구, 거리, 시간, 확인일, 경로 원천 링크.
- important distinctions: '확인되지 않음' ≠ '거래 없음', '호가' ≠ '계약 체결가', '직선거리' ≠ '보행거리'.
자동 확인된 근거와 수동 입력 메모는 출처를 구분하고, 만료되거나 충돌한 근거는 경고한다.

## 8. 검증 예시 및 완료 조건

예시 입력: '스타필드 수원 / 수원 장안구 / 도보 / 희망 20분 이내 / 전체 거래 / 예산 미설정'.
근무지 주소: 수원시 장안구 수성로 175.
후보 이름은 실제 위치 대조 후 선택. 후보 예: 화서역파크푸르지오, 화서역푸르지오브리시엘, 꽃뫼노을마을풍림, 꽃뫼노을마을한마루, 화서역파크뷰. 여기서 가격/도보 20분 이내 여부는 검증 전까지 확정 금지.

Codex 완료 조건:
1. 원고에 10초 비교/이동 동선/주거비/실거주/Q&A/결론·3줄 요약이 정확한 순서로 출력.
